# 工控控制流程与故障范式

本文档将两个典型控制循环抽象成可独立理解的工控代码范式。它不要求读取任何外部仓库或项目代码；示例中的 `MotionLoop`、`HardwareManagerLoop` 和相关类型只是帮助理解业务流程的概念名称。

## 应继承的范式

### 统一入口和类型分派

`PipelineCommand` 使用 `std::variant` 表达 Position、ServoJ 和 ServoCart 三类互斥输入，在 `PipelineCore::pushCommand()` 处集中分派。后续模块不应为每种命令复制一套平行入口。

适用规则：

- 互斥输入使用一个统一入口；
- 在一个边界完成类型分派；
- 让每种输入路径的接受条件、失败状态和状态影响清楚可见。

### 固定大小的公共数据

`runtime/common/` 使用固定大小结构、`std::array`、显式 `AxisCount`、`BranchId` 和 `SegmentId`。跨模块数据应优先采用这种形式，明确容量和有效数量。

不要把固定容量误解为有效数量，也不要把普通整数参数混用为不同领域的 ID、单位或状态。

### 单一中间模型

Position 路径由 `Segment` 贯穿 SegmentBuilder、ScalarBuilder、BlendBuilder 和 Sampler。新增阶段先判断能否扩展现有 `Segment` 或已有元数据，不要平行创建另一套 Path、Trajectory 或 Execution 模型。

### 显式上下文

FK、IK、段构造和采样显式传递 `BranchId`、轴数量和 seed 等上下文，不从 solver 的可变成员或上一次调用隐式推断。需要上下文时，将其放入参数、值对象或明确的执行上下文中。

### Runtime 与 Pipeline 的职责

Runtime 负责生命周期、状态和诊断门面；Pipeline 负责命令路由、规划、缓冲和采样。按职责分层，而不是按文件数量分层。对外接口应保留稳定门面，内部路径可以使用私有 helper 和组合对象。

### 阶段边界

`Runtime::sample()` 是控制周期入口，规划、IK、文件 I/O、网络和诊断序列化不应无意间进入其中。新增代码先判断属于初始化、输入/规划、控制周期还是诊断/管理阶段。

## 业务流程范式

### 固定决策阶梯

遇到一个保护分支时，按以下顺序判断：

```text
真实业务情况？
→ 不可信输入边界？
→ 当前模块的业务不变量？
→ 正常拒绝、外部不可用，还是内部不变量破坏？
→ 是否有明确 fallback 策略？
→ 顶层能否定位根因？
```

没有明确责任和失败分类时，不要继续增加保护分支。模块应信任已经写入契约的上游前提，同时坚定维护自己拥有的不变量。

### MotionLoop：规划域的一次迭代

将一次运动规划迭代组织成连续的业务链：

```text
对齐当前硬件姿态
→ 排空运动命令
→ 确认 Runtime 已同步
→ 在预算内推进规划
→ 采样当前运动点
→ 将完整样本写入 Servo 队列
→ 发布 Runtime 快照和完成事件
```

要点：

- 对齐失败时，不进入规划和采样；
- 规划预算和下游队列容量是流程中的显式边界；
- 样本完整写入后，才发布对应的完成事件；
- 一次迭代结尾统一发布快照，而不是让各个阶段分别发布状态。

### HardwareManagerLoop：硬件域的一次迭代

顶层循环只保留两个清晰阶段：

```text
Transport 阶段：命令、连接、管理请求、状态读取、诊断
→ Servo 阶段：反馈、安全、输出准备、硬件发布、周期提交
```

Servo 阶段进一步保持如下顺序：

```text
读取反馈和一个规划样本
→ 评估最终安全许可
→ 准备编码器输出
→ 保留待提交目标候选
→ 尝试发布硬件命令
→ 仅在发布接受后提交外部可见目标
→ 发布安全决策和周期计数
```

这里的顺序本身就是行为契约：安全决策必须先于硬件输出，外部目标必须在硬件接受后才提交，诊断日志应通过计数器延迟到非实时 Transport 阶段。

### 命令处理范式

将命令处理写成可读的业务管线：

```text
查找命令目录
→ 判断执行领域
→ 拒绝不属于本域的命令
→ 修改持久意图或提交服务请求
→ 保存请求身份
→ 等待并发布最终 ACK
```

不要把命令分类、状态修改、硬件写入和事件发布拆到多个无法从名称看出关系的通用函数中。

### 何时拆分，何时保持连续

保持一个函数连续，当它描述的是一个完整且单一的业务事务，即使它有较多局部步骤。拆分函数，当拆分后每个函数都能表达清晰的业务阶段、不变量或副作用边界。

优先提取：

- 纯判断，例如 `isCompleteFeedback`；
- 明确阶段，例如 `evaluateSafety`、`prepareOutput`；
- 明确提交点，例如 `publishAndCommit`；
- 独立的诊断或恢复动作。

避免提取：

- 只有一两行、没有独立语义的包装函数；
- 仅以 `process`、`update`、`handle` 命名的技术碎片；
- 会让调用者看不到状态修改顺序的隐藏副作用。

### 注释的两层结构

在公开接口或函数契约中说明输入、输出、所有权、线程、阶段和失败语义；在实现中只标注业务阶段、执行顺序、提交点和非直观原因。不要逐行解释语法，也不要在头文件和实现中重复维护同一大段流程说明。

### 唯一提交点

将候选计算和外部副作用分成两个阶段：

```text
读取并验证
→ 计算候选结果
→ 通过安全门
→ 提交硬件或外部状态
→ 仅在提交接受后发布完成状态
```

安全决策、硬件写入、目标快照和完成事件之间必须有清晰的先后关系。不要让多个 helper 分别修改持久意图、写硬件和发布状态，使真正的提交点不可见。

## 契约与故障范式

### 只对正确输入负责

每个模块先声明自己的正确输入，再决定自己负责哪些检查：

```text
传输边界：帧、大小、版本、序列完整性
协议边界：消息类型、字段组合、编码合法性
业务边界：状态、权限、单位、范围、容量
算法内部：算法前提和内部不变量
```

上游已经负责的检查，下游不要重复实现；下游真正拥有的业务不变量，不能假设上游一定替自己检查。发现不属于本模块职责的错误时，报告错误并终止当前流程，不要擅自修正输入。

### 正常拒绝和故障分离

```text
命令不满足公开业务条件      → 正常拒绝
硬件暂时不可用               → 明确 unavailable/degraded
内部不变量被破坏             → 硬失败并进入 fault
安全策略主动禁止输出         → 明确 inhibited/safe 状态
已接受动作执行失败            → 操作失败事件和故障上下文
```

不要把这些情况都压缩成 `false`，也不要用“读取失败就返回上一帧”“转换失败就返回零值”“未知状态按正常处理”等方式让流程假装成功。

### 故障闭环

一个完整故障处理过程应形成闭环：

```text
检测根因
→ 分类故障
→ 停止受影响的业务链
→ 发布安全输出或明确禁止状态
→ 记录模块、阶段、操作、错误码和上下文
→ 向顶层投影可定位状态
→ 通过显式 reset/clear/recover 恢复
```

重试只能作为明确策略存在，并需要边界、周期、终止条件和对外状态。日志不能代替故障快照；上层只能补充上下文，不能把底层根因改写成无意义的通用错误。

### 防御性代码审查问题

遇到一个 `if`、默认值、`try/catch` 或 fallback 时，先问：

1. 这是哪个边界的责任？
2. 输入在这里是否应该已经满足契约？
3. 失败是调用者可修正的拒绝，还是系统故障？
4. 如果继续执行，后续结果是否仍然有业务意义？
5. 顶层能否知道具体模块、阶段和根因？

如果问题没有明确答案，优先建立契约和故障模型，而不是继续添加保护分支。

### 契约债务和故障债务

对暂时保留的契约假设或不完整故障分类，可以使用可检索标记记录：

```cpp
// industrial-contract: 此层信任上游已完成协议长度校验。
// industrial-fault-debt: 当前仅区分 transport unavailable；补齐驱动码后拆分恢复策略。
```

标记必须同时说明当前假设、适用范围和升级条件；它记录的是有意识的边界，不是跳过实现的借口。

## 需要有条件使用的范式

### 非拥有依赖

非拥有依赖可以用于外部提供的 solver、驱动、共享内存映射或服务对象。这个模式可以保留，但必须明确：

- 使用者不负责释放外部对象；
- 外部对象生命周期必须覆盖使用者；
- 含有可变工作区的对象不得并发调用；
- 如果所有权需要转移，应改用 `std::unique_ptr` 或明确的所有权接口。

### 可增长容器和实时性

可增长容器适合初始化、配置和规划阶段，但不能因此推导出控制周期可以任意分配或搬移元素。控制周期中的容器操作必须经过容量、复杂度和最坏耗时检查。

### 日志出口

统一标签和可关闭 sink 是合理方向，但同步输出、flush、非原子配置和格式化成本不应直接复制到控制周期。正式工程应把日志出口、线程安全和实时限制写成明确契约。

### 文件长度和接口数量

存在超过 500 行但仍然保持单一业务流程的合理实现文件，因此不要把“文件超过 500 行”或“public 方法超过 10 个”作为硬性违规。使用职责混杂、状态耦合、分支复杂度和阅读路径作为拆分依据。

## 自包含边界

本参考只定义代码组织、契约边界和故障处理范式。理解或使用本 Skill 不需要读取任何其它项目文件；实际修改代码时，仍应按照主 Skill 的工作协议读取当前任务所需的接口、测试和事实文档。
